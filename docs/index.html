Terra

Vehicle body and onboard autonomy for autonomous rovers

⚠️ Warning

Terra is an active research system. Bluetooth actuator control, radio sessions, and physical compatibility remain unverified. The optional bench procedure requires separate authorization.

Architecture

The phone is the whole rover brain. Swift reads the sensors and drives the motors; every decision in between happens in the Rust crate terra-av, linked into the app as a static library. Depth also streams to the base station over Zenoh.

Inside terra-av

Each stage is a trait; each algorithm is one implementation. terra-av.toml picks one implementation per stage, so swapping a planner or a vehicle is a configuration change.

Shared Rust Crates

Terra is built as a collection of modular Rust crates. The core autonomy pipeline lives in terra-av, while the phone bridge and rover runtime have dedicated crates.
CrateDescription
terra-typesSensor samples, coordinate conventions, commands and motor outputs.
terra-actuatorsConfigurable actuator layouts, routing and Bluetooth framing. Editable examples require capability validation and explicit port selection for ESC/servo templates.
terra-stateVIO velocity anchors with bounded IMU prediction.
terra-controlDifferential-drive velocity PI control, feedforward, anti-windup and freshness checks.
terra-waypointLat/lon go-to-waypoint follower. The phone imports it through terra-mobile as MobileWaypoint. TerraPhone's Waypoint section selects the goal and runs that follower.
terra-motorsSigned wheel effort to PWM duty and direction, with a hardware enable gate and a command watchdog.
terra-mappingRolling local occupancy grids from depth and camera poses.
terra-transportLeased Zenoh velocity publishing. Default prefix is terra/rover.
terra-mobileUniFFI interface between the Swift app and Rust.

Applications

TerraPhone (iOS)

The phone is Terra's sensor head and motor link. It does two things: read the phone's sensors, and send wheel commands to the rover. Every decision in between happens in the Rust crate terra-av.

Two-loop architecture:

Floorplan:
Planner loop, 20 Hz:   PhoneSensors ─► SensorFrame ─► TerraAv.tick ─► DriveCommand (target + measured twist)
                                           ▲ e-stop        ▲ Goal (joystick)

Velocity loop, 50 Hz:  latest DriveCommand ─► VelocityController ─► BluetoothLink ─► Pi

The two loops share only the latest command, so a slow planner tick never
delays the motors. The velocity loop stops if the target is older than 0.3 s.
FolderJob
Sense/ARKit pose, gyro, GPS, thinned LiDAR depth. Raw, in each sensor's own frame.
TerraAV/Phone helpers for the generated terra-av types (Vec3, VioPose from ARKit).
../Generated/Built by the script, not committed: TerraAV.swift bindings + TerraAV.xcframework.
Drive/Joystick → Goal.velocity.
Motors/VelocityController (twist → wheel effort, P + feedforward) and the Bluetooth link to the Pi.
App/RoverLoop (the two loops) and the one screen.
Resources/terra-av.tomlWhich algorithm runs in each stage, plus the phone mount.

The phone mount (rotation and camera offset) lives in terra-av.toml, not in the app.

Operational replay (tools/observability)

Install from that directory with uv sync --frozen (Python 3.12+). The lockfile pins the Rerun SDK and viewer to 0.39.0; review recordings with the matching viewer.

# Export a source journal, or a directory with events.jsonl + attachments/<sha256>
uv run terra-replay export /path/to/events.db --rover 4 --session RUN_ID --output /tmp/run.rrd
uv run rerun /tmp/run.rrd

# Download a scoped recording from the collector (reader token file mode 0600)
uv run terra-replay fetch https://HOST/observability --token-file /private/reader.token \
    --rover 4 --session RUN_ID --output-dir /tmp/rover-run
uv run rerun /tmp/rover-run/recording.rrd

# Synthetic demo fixture (not a physical run; regenerate with tests/make_demo.py)
uv run terra-replay export tests/fixtures/demo --output /tmp/demo.rrd
uv run pytest tests
  • Find session IDs with authenticated GET /observability/v1/sessions or from the source journal. Credentials go in the Authorization header, never in URLs or recordings; fetch does not follow redirects.
  • An export also writes .events.jsonl, .index.json and .manifest.json, keeping event identity, source/receipt time, gap count, revision and clock uncertainty. Late events create a new revision; source events are never renumbered and no drive commands are sent.
  • The default layout shows event text, motion curves, occupancy (unknown is gray), camera/depth and 3D ground/obstacle boundaries. Missing attachments stay explicitly missing, and stale channels are cleared so an old image never appears registered to new depth. Simulator RGB is shown separately from calibrated depth.
  • wall_clock_approx is approximate across machines; estimated_server_time uses measured RTT offset where available (drift is not measured). Per-producer boot sequences are authoritative for ordering.

Sensor timing (tools/sensor_timing)

Splits the age of the newest IMU sample at each control tick into hops, to tell whether a stale_imu hold came from iOS or from Terra. A bare logger with its own CMMotionManager records what iOS delivers with none of Terra's code in the way.

CoreMotion sample ──iOS delivery──▶ motion handler ──Terra queue──▶ terra.control ──push──▶ Rust
  t_sensor                            t_os                              t_queue                t_done

# Fetch recordings from the phone, then analyse
xcrun devicectl device copy from --device <id> --domain-type appDataContainer \
  --domain-identifier org.terra.robotics.phone --source Documents/SensorTiming \
  --destination ~/terra-logs/sensor-timing
python3 tools/sensor_timing/analyze_sensor_timing.py ~/terra-logs/sensor-timing/*.csv --json summary.json --plot plots/
python3 -m unittest discover tools/sensor_timing
CauseMeaning
ios_sensor_gapiOS produced no IMU sample in the window.
ios_deliveryThe sample existed but iOS had not called the handler yet.
terra_queueThe handler had it, but terra.control was busy (blocker named).

Conditions C0–C5 step from a still rover with only the bare IMU logger up to full tracking, YOLO and FPV while driving; run C2 and C4 in both Debug and Release. Recording needs the Sensor timing debug screen, which the slimmed TerraPhone no longer has.

Detector model (models/yolo26n-rover)

YOLO26n trained on ball, blue bucket and orange bucket (100 epochs, 640 px; val mAP50 0.95, precision 0.95, recall 0.93; see results.csv). It was used as RoverDetector.mlpackage for target search; the current TerraPhone does not bundle it.

pip install ultralytics coremltools
yolo export model=weights/best.pt format=coreml nms=False half=True imgsz=640

nms=False keeps YOLO26's end-to-end head: one [1, 300, 6] output, rows [x1, y1, x2, y2, score, class] in 640 px input coordinates, duplicates already removed. The package was exported with ultralytics 8.4.190, coremltools 9.0, torch 2.7.0 and numpy 2.5. That coremltools fails on numpy 2.5 with “only 0-dimensional arrays can be converted to Python scalars”; change dtype(x.val) to dtype(x.val.item()) in _cast in coremltools/converters/mil/frontend/torch/ops.py.

# Tile worlds and the go-to-waypoint contract are documented in:

⚠️ Build

The script generates the Swift bindings from crates/terra-av/src/ffi.rs, builds the static library for device and simulator, bundles apps/ios/Generated/TerraAV.xcframework, and regenerates the Xcode project. Re-run ./scripts/ios/build-ios.sh after any Rust change.

Status: The app calls the real Rust TerraAv.tick. It returns a zero twist until the pipeline stages are implemented. Bluetooth, sensors, joystick and e-stop are real.
