## Exact APIs for Task 8

Generated same-module Swift functions: actuatorValidateLayout(layoutJson:capabilitiesJson:) throws -> String returns JSON array of errors, actuatorRoute(layoutJson:inputJson:) throws -> String returns full [{id,value}], actuatorEncodeFrame(frameJson:) throws -> Data, actuatorFragment(messageId:payload:maximumWriteLength:) throws -> [Data]. Rust names use snake_case; validation/route follow task1 typed schemas and unknown fields reject. Frame JSON requires kind string drive/arm/disarm/emergency_stop, session/revision/sequence u32 and values array (empty for controls); u32 max sequence rejects. Wrapper errors are MobileActuatorError.InvalidInput(message).

BluetoothLink ObservableObject publishes on main queue: status, peripheralsJSON [{identifier UUID string,name}], connectedIdentifier UUID?, statusJSON full periodic status only, capabilitiesJSON, layoutJSON, replyJSON last configuration or command_acceptance event, isReady, armed, arming. Operations: scan(), connect(identifier: UUID), disconnect(), drive(valuesJSON: String, producedAt: TimeInterval), send(frame: Data, producedAt: TimeInterval), request(envelope: Data), arm(), disarm(). Prefer drive to own sequence internally. producedAt must be ProcessInfo.processInfo.systemUptime in same monotonic domain, supplied when new sample/target was produced. Produce fresh routed full values at20Hz. Samples age>=100ms drop without timestamp refreshing. Raw send preserves supplied header and rejects stale session/revision/sequence.

arm() first creates a fresh complete safe DRIVE from current layout (servo configured safe position; disabled servo uses clamped center, propulsion zero). It awaits the corresponding explicit accepted command_acceptance before queuing ARM; ATT acknowledgement alone never sets applied/armed state. While disarmed/arming ergonomic drive substitutes freshly produced safe values; it allows normal values only after periodic armed status. It does not replay targets on reconnect. Safe acceptance wait expires300ms. Status gap>=300ms or outstanding ATT write>=100ms closes connection and requires explicit recovery; disconnect invokes Pi disarm. Only one ATT with-response write outstanding; pending drive replaces earlier pending drive, disarm clears pending drive and preempts remaining chunks at next ATT boundary; failed writes never retry motion.

Requests use task2 exact schema numeric request_id; stage/commit payload requires staged_revision plus staged_request_id of exact stage. Link synchronization allocates IDs1,2 initially; externally supplied IDs should start elsewhere (e.g.1000); all used IDs retained until disconnect and reuse rejects. Replies correlate by request_id/operation. Capabilities + layout matching current status revision unlock readiness. After committing a changed layout request capabilities/read_layout with fresh IDs to resynchronize. Mutation UI should remain disarmed and show remote errors.

## Pairing and transport

Scan service0010 by advertised service UUID; explicit peripheral selection by stable CoreBluetooth UUID, names displayed. Discover then read encrypted status0012 before subscribing status/replies0014. This admits bonded owner to BlueZ; initial null session can precede admission, readiness waits periodic nonnull session. Setup status-only service is accepted: encrypted read triggers iOS pairing, user confirms matching code on Pi and phone; successful setup reply closes link and instructs user to start normal service and explicitly rescan/reconnect. No writes exposed during setup.

Characteristic callbacks require current peripheral, session generation and characteristic object identity; reconnect is blocked until cancellation's disconnect callback retires prior connection. Assemblers are independent per status/reply, bounded16KiB, expire100ms and reject duplicate/order/count conflicts. Full raw JSON long-read values parsed independently of notification headers. Reply reads are polled every200ms while requests remain outstanding so large replies that exceed255 notification fragments can be recovered through ATT long read. Negotiated maximumWriteValueLength(.withResponse) drives Rust fragmentation; no fixed MTU assumption. Active/pending message IDs excluded from wrap allocation. Status command_acceptance remains separate from periodic status.

Real pairing, radio long reads, queue scheduling and generated API spelling/types need execution review under a later authorized build/hardware phase. This implementation provides no measured timing guarantee.
